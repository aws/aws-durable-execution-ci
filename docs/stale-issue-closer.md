# Stale issue closer

The reusable stale-issue-closer workflow closes issues that are waiting on a
response. It targets open issues carrying the `needs-info` label and closes any
that have gone without a reply for a configured number of days (14 by default).

## Behavior

For each open issue that carries `needs-info`, the workflow:

1. Reads the issue timeline and finds the most recent time `needs-info` was
   applied. This timestamp starts the response window.
2. Finds the most recent comment on the issue. **Any** comment resets the
   window, regardless of who wrote it — a reply from the reporter or a
   maintainer both count as a response.
3. Computes the effective last activity as the later of the label time and the
   most recent comment time. If that is at least `days-until-close` days ago,
   the workflow posts the closing comment and closes the issue.

Issues still inside the window are left untouched. Pull requests are ignored.

Removing the label (for example, once the reporter responds and a maintainer
acts on it) takes the issue out of scope on the next run.

## Usage

Scheduling lives in the consuming repository, because a reusable workflow cannot
schedule itself. Add `.github/workflows/stale-issue-closer.yml`:

```yaml
name: Stale Issue Closer

on:
  schedule:
    - cron: "7 12 * * *" # daily at 12:07 UTC
  workflow_dispatch:

permissions: {}

jobs:
  close-stale:
    permissions:
      contents: read
      issues: write
    uses: aws/aws-durable-execution-ci/.github/workflows/stale-issue-closer.yml@<full-commit-sha>
```

Replace `<full-commit-sha>` with the 40-character commit SHA to use.

Scheduled workflows run only from the version of the file on the default branch,
are queued (GitHub can delay or drop runs scheduled at the top of the hour, so a
minute like `:07` is preferred), and are automatically disabled after 60 days of
repository inactivity.

## Configuration

| Input | Default | Description |
| --- | --- | --- |
| `days-until-close` | `14` | Days without a response before an issue is closed. |
| `close-reason` | `not_planned` | State reason applied when closing. One of `completed`, `not_planned`, or `duplicate`. |

The close comment is generated by the script and includes the configured
`days-until-close` value.

## Repository setup

No secrets, environment, or cloud credentials are required. The workflow uses
the automatic `GITHUB_TOKEN`; the caller grants it `issues: write`. The target
label must exist in the consuming repository (`needs-info` is part of the shared
[issue-triage](issue-triage.md) taxonomy).

## Security model

The generation job checks out only `scripts/close_stale_issues.py` from the
workflow's immutable revision and never checks out the consuming repository.
Issue titles, bodies, comments, and label names are only read; the script uses
them to decide whether an issue is stale and never executes them. All GitHub API
access goes through the `GITHUB_TOKEN` scoped to `contents: read` and
`issues: write`.
